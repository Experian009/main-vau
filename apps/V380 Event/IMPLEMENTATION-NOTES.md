# Аудит и исправления V380 Event MVP

## Итог

Проект был проверен относительно заявленной локальной event-only архитектуры. Базовая цепочка просмотра существовала, но она не образовывала надёжный рабочий pipeline уведомлений и архива: интерфейс оставался демонстрационным, запуск не защищал от гонки готовности сервисов, а обработчики событий не предоставляли статуса и не гарантировали корректный жизненный цикл локальных файлов.

Исправленная версия реализует локальный pipeline **decoder → MediaMTX → gateway → motion → Telegram/TeraBox**, добавляет наблюдаемость в UI и сохраняет исходную модель безопасности: камера, Telegram и TeraBox credentials остаются только в `.env.windows`.

Дополнительно исправлена установка TeraBox: исходный `package.json` ссылался на несуществующий Git tag `v3.3.1`. Фактический tag репозитория — `app-3.3.1`. Windows installer теперь использует правильный tag, а при ошибке GitHub-загрузки Bun автоматически пробует официальный codeload-архив и npm fallback. В upstream archive также удаляется только некорректная self-link dependency `terabox-node: link:`; приложение uploader от этого не меняется.

## Выявленные расхождения

| Область | Исходное состояние | Исправление |
|---|---|---|
| Запуск Windows | `motion` стартовал почти одновременно с decoder/MediaMTX и завершался при временно недоступном RTSP. | Launcher ожидает decoder API и gateway; motion service выполняет повторное подключение к RTSP каждые 5 секунд. |
| Motion event | Детектор и сохранение были реализованы, но event-клипы создавались с низкой частотой и разрешением анализа. | Детекция осталась экономной, а запись отделена в поток до 10 FPS и ширины 1280 px. Telegram файл ограничивается `POSTBUFFER_SECONDS`. |
| Telegram | Не было UI-статуса и нечёткая конфигурация могла молча отключить доставку. | Добавлены health endpoint, валидация парных Telegram переменных и видимый результат отправки по событию. |
| TeraBox | Worker мог начать обработку до завершения notification; uploader создавал служебные файлы рядом с оригиналом. | Archive ждёт готовые JSON-метаданные, работает со staging-копией, проверяет текстовый результат uploader и удаляет оригинал только после подтверждения. |
| Наблюдаемость | Browser видел только WebRTC и PTZ; навигация, demo image и часть кнопок не соответствовали локальной архитектуре. | UI теперь содержит рабочие «Камера», «События», «Архив» и «Настройки», очередь, историю и health motion/Telegram/TeraBox. |
| Документация | Главный README оставался шаблонной документацией Astro/Ploy. | README и Windows guide описывают фактический локальный продукт, переменные, запуск, диагностику и границы MVP. |

## Проверки

| Проверка | Результат |
|---|---|
| `bun run verify` | Пройдена: lint, Astro type check и production build. |
| `node --check` для gateway/motion/notifier/archive | Пройдена. |
| `node scripts/test-local-services.mjs` | Пройдена: gateway authorization, WHEP path rewrite, event-status aggregation, motion retry health, notifier health и archive health. |

Проверки выполнены без реальной камеры, без Telegram token и без TeraBox cookie. Поэтому они подтверждают корректность локальных контрактов, очереди и интерфейсных интеграций, но не могут подтвердить конкретные учётные данные или состояние внешних сервисов пользователя.

## Установка обновления

1. Остановите старую версию командой `windows\stop.cmd`.
2. Сохраните резервную копию действующего `.env.windows` и при необходимости папки `local-data\events`.
3. Распакуйте исправленный архив поверх исходной папки либо в новую папку.
4. Верните `.env.windows`; сверяйте его с обновлённым `.env.windows.example` и добавьте новые необязательные параметры записи, если нужны.
5. Выполните `windows\setup.cmd`, затем `windows\start.cmd`.
6. В браузере откройте `http://localhost:3000`, нажмите **«Подключить»** и введите `http://localhost:8787` и существующий `GATEWAY_TOKEN`.
7. Откройте **«События»** и убедитесь, что все три сервиса показывают ожидаемый статус. При проверке движения начинайте с объекта в кадре и смотрите `motion.err.log` при отсутствии события.

## Оставшиеся границы MVP

Исправленная версия по-прежнему является single-camera event-only MVP. Она не создаёт 24/7 запись, 30-минутные сегменты, распознавание людей/автомобилей, многопользовательский Telegram bot или публичный доступ к камере. Надёжность доставки зависит от постоянно работающего Windows компьютера, рабочей V380 Cloud сессии, действующей Telegram bot configuration и актуальной TeraBox cookie `ndus`.
